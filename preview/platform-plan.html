Bilby · Nextwave.au · architecture

Building for the second product before there is a first customer

eSIM is category one. This is the plan that lets category two arrive later without a data migration on a live ledger, and the short list of things that have to change now because they stop being free the day someone pays.

Companion to PLATFORM.md Status: proposed Phase 0 not yet started

Take money in AUD, buy an entitlement from a supplier in USD, deliver a credential to a traveller, support them when it fails, and account for the difference.

That sentence is true of an eSIM, a data top up, a VPN config and a gift card. None of it mentions an ICCID. The part that never mentions an ICCID is the platform. Everything that does is a category.

02 · Where we are

What the shortest path to a working eSIM assumed

Not a criticism of the code. Building the direct path first was correct. This is simply the inventory of what it took for granted.

Two of these are worse than they look

The catalogue is not stored. It is fetched from the supplier on every request and priced on the fly from wholesale times a margin constant. So the price can change between the plans page and checkout, there is no stable SKU to write on an order, everything is in USD, and GST appears nowhere. It blocks the second product, and it blocks the first one harder.

The pricing module is a liability, not just dead code. It carries regional wholesale figures seeded from published estimates rather than from a signed rate card. Those numbers must not quietly become the basis of retail pricing. Quarantine it, do not repurpose it.

03 · The work

Five seams that cost a day now and a migration later

Nothing else in this plan is urgent. These are, and they are urgent precisely because there are no customers yet.

Seam 1

An order is money. An order item is a thing.

Today every order has exactly one item, so splitting the table costs nothing. It is the row shape that makes a bundle possible later, and the row shape that makes a partly failed order describable now. If provisioning fails after Stripe has captured, there is currently nowhere to write that down.

-- money, product agnostic, never grows a category column
orders       id · user_id · status · sell_currency · sell_amount
             tax_code · tax_amount · discount_code · discount_amount · stripe_ref

-- what was bought. category lives here, never above.
order_items  id · order_id · sku · category · fulfiller_id · supplier_ref
             cost_currency · cost_amount · fx_rate · status · attempts · last_error
Cost nowOne migration on an empty table.
Seam 2

Money is four currencies, a rate, and a tax code

You sell in AUD and buy in USD, so margin is unknowable unless the rate used that day sits on the order. GST is roughly one eleventh of an Australian retail sale, larger than the payment fee and the FX spread combined. Whether a particular sale is GST free is your accountant's answer rather than the code's, so a tax code sits on each order. And the customer may see and pay a different currency again, which has to be recorded or support cannot answer someone who writes in saying they paid EUR 18.40 against an order that reads AUD 29.00.

orders + presentment_currency · presentment_amount (what they actually saw)
         tax_country · tax_evidence (two non contradictory signals, collected at sale)
Cost laterAdding the tax column after real sales means restating figures already reported. Location evidence cannot be collected retrospectively at all.
Seam 3

A stored catalogue with SKUs that are yours

This turns "suppliers are a registry, not a choice" from a sentence in the decisions file into something that exists. A SKU is yours and permanent. A source is theirs and swappable. Changing supplier for Japan becomes an update to one row, and last month's orders still point at whoever actually served them.

catalog_items    sku · category · title · tax_code · active
                 attributes (category specific shape, as JSON)

catalog_prices   sku · currency · sell_amount · is_default
                 one row per pricing currency. today exactly one, in AUD.

catalog_sources  sku · fulfiller_id · external_id · cost_amount · priority · enabled
Side effectThe plans page and checkout finally read the same number from the same place.
Seam 4

Entitlements, so the dashboard lists things you have

The eSIM table stays exactly where it is. It is the right home for ICCID, activation code and install state. An entitlement points at it. What this buys is a customer dashboard that lists things you own rather than your eSIMs, and it buys it while the list has only one kind of thing in it, which is the only moment the change is free.

AlsoThe supplier interface gains a cancel method and declared capabilities, because whether an unactivated profile can be handed back is the largest single input to net margin.
Seam 5

Idempotency, the one that costs real money if skipped

There is none today. Stripe retries webhooks. Suppliers time out after doing the work. Users double click. Every one of those paths currently ends at "provision an eSIM", and two of them can run twice. The failure it prevents is provisioning two profiles against one payment, and you cannot get the second one back, because it is activated.

idempotency_keys  key ('fulfil:' || order_item_id) · scope · result · created_at
RelatedThis is why supplier idempotency support is question eight on the eSIM Access list.

04 · Kits

A bundle is a join table, once seam one exists

A kit is a catalogue item whose fulfilment fans out to more than one fulfiller. One SKU, one price, one tax line, two order items, two entitlements. Nothing else changes, because an order is already a list of items.

Do not build the bundle table yet

Build seam one so that the bundle table is possible. That distinction is the entire discipline of this plan: create the shape, not the feature. Bundling is worth making trivial because it is the only defensible commercial position available, since competing on the price of a commodity data plan against better funded companies is a losing game. It is not worth building while there is nothing to bundle.

05 · Reach

Currency is four decisions, and only one of them is expensive

Nothing here locks Bilby to Australian customers. The word currency collapses four separate things, and keeping them apart is what makes serving a second market a tax question rather than a rebuild.

DecisionWhat it isWho decidesCost to change
SettlementWhat lands in the bankYour bank and your entityHigh
PricingThe currency a price is set inA person, per marketA price list somebody maintains
PresentmentWhat the customer sees and is chargedDetected at checkoutNear zero. A setting.
MarketWhose customers you serveTax registration and lawThe real one
Free

Local currency costs you nothing, so it is not an architecture problem

Stripe Adaptive Pricing presents and charges in the customer's local currency across more than 150 countries, with Australia supported as a merchant country. It picks the currency, converts at a rate guaranteed through settlement, and unlocks local payment methods that only work in local currency.

Per Stripe's own documentation, you pay nothing. The customer pays a 2 to 4 percent conversion fee built into the rate they are shown, and avoids it entirely by choosing to pay in your currency instead. Refunds go back at the original rate, so a refund costs you nothing extra either.

SchemaThe session still reports your currency. What the customer saw arrives in a presentment details hash, which is the source for the two new columns in seam two.
ConstraintIt does not work with Elements on the Payment Intents API. Phase 1 must use Checkout, or this option quietly closes.
Rule

Detect once, pin it, and never re price

Detect location at the start of the checkout session and hold it. A detected location must never change a price the customer has already been shown. Use detection for currency and language only, never to gate access, and never as tax evidence on its own, because one signal is not two.

Gate

What actually stops you selling into a second country

Not the currency and not the code. Tax registration and consumer law, country by country. The EU requires two pieces of non contradictory evidence of where a consumer is before you can treat the sale correctly, and the United Kingdom, New Zealand, Singapore and Japan each run their own scheme with their own thresholds and registration.

There is a quieter consequence too. Australian GST treatment is not the same for a sale to a non resident as for a sale to an Australian. That is exactly why the tax code sits on the order instead of being a constant, and it is a question for the accountant before the first sale abroad rather than after it.

What is actually Australian about BilbyThe support hours, the trust story and the page copy. All marketing, none of it in the schema.

06 · Restraint

Written down so it can be pointed at later

not now

A second category

Until eSIM has paying customers, a signed supplier, and a refund process that has survived a real refund.

not now

A cart

One item per order until somebody actually asks for two.

not yet

A second pricing currency

One pricing and one settlement currency, both AUD, until a second market is tax registered. Showing local currency is not covered by this and can be switched on whenever it helps.

not now

Microservices

One Next.js application, one Postgres. The complexity budget belongs to fulfilment.

not now

Automatic supplier failover

A person flips a row in the console. Automatic failover on a half working supplier provisions half a catalogue at the wrong rate.

never

A wallet or stored value

Issuing stored value is a regulated activity in Australia. Discounts and refunds only.

07 · Sequence

What happens in what order

The numbering is real. Each phase depends on the one before it, and only the first one is urgent.

Phase 0 · now

The five seams

No new features, nothing a customer can see, no second product. Two to three working sessions. Happens before supplier credentials arrive, so the adapter has somewhere correct to land.

Phase 1

eSIM end to end

Supplier adapter against a sandbox, catalogue seeded by hand for the launch destinations, Stripe Checkout rather than Elements so local currency stays available later, webhook driven fulfilment, credential delivered. Done means a real card charging a real dollar and a real profile installing on a real handset.

Phase 2

Operations

Refund and cancel in the console, failed order retry, usage view, and a margin calculator that takes the rate card, the Stripe fee, an FX buffer, GST and a refund reserve. This phase decides whether the business survives contact with customers.

Phase 3

The Android app

Against the API origin already frozen into the binary. The R8 crash bisect is still open.

Phase 4

A second supplier

One more row in the sources table. This phase exists to prove the registry works while the stakes are low, not because a second supplier is needed.

Phase 5 · gated

A second category, and only with revenue

Data top ups first, on the reasoning already recorded: same customer, no new regulator.

08 · Proof

An architecture claim that cannot fail is worth nothing

So here is one that can. Adding a second category must touch exactly four kinds of file: one fulfiller adapter, one attributes shape, one detail panel, one console tab. If it touches commerce, tax, authentication, the order pipeline or the entitlement table, the abstraction failed.

A new fulfiller adapterexpected
An attributes shape: operator, country, face valueexpected
A detail panel showing the receipt and confirmation codeexpected
A console tabexpected
Commerce, tax, authenticationuntouched
The entitlement tableuntouched
Carrying a customer supplied value from checkout to the fulfillerfailed

The test found one thing, which is why it exists

A data top up needs something from the customer at purchase time: the phone number being topped up. An eSIM needs nothing. Nothing in the model carried a customer supplied value from the checkout form through to the fulfiller, so a second category would have had to bolt one on, and would most likely have bolted it onto the order.

The fix is two columns, added in Phase 0 while they are still free: an input schema on the catalogue item describing what to ask for, and an input record on the order item holding what the customer actually gave. Frozen on the item, because "you sent it to the wrong number" is a support conversation that needs evidence.
